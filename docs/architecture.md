# Custom header layout

The library replaces internal `UINavigationBar` frame manipulation with a screen-owned `NavigationHeaderView`. Its minimum deployment target is iOS 15; it has no external dependencies or resource bundles.

`CustomNavigationController` owns the UIKit stack, theme, status-bar policy, and public edge-gesture admission gate. `CustomNavigationViewController` owns a header and safe content layout guide. It can be subclassed or contain an existing controller. UIKit moves the whole screen and header together through push, pop, and cancellation, avoiding a separate header whose state needs repairing after transitions.

The header begins at the top safe-area anchor. A backdrop of the same color fills the top inset. Its preferred compact height grows when the two-line title requires more room. An app-owned `UINavigationBar` renders original `UIBarButtonItem` objects at its normal row height. Directional outer insets and a clamped vertical offset move that row. Plain owned slot views reserve horizontal space for the title and automatic Back control. The title renders outside the native bar's text-size environment so Dynamic Type can expand it; Back retains a 44-point touch target. Their horizontal positions come from those owned slots using public coordinate conversion.

Large titles occupy a separate region below the compact row. With an explicitly selected scroll view, the content guide stays below the compact row and a constant additive content inset reserves the full expansion. Normalized scroll distance shrinks the visible title region. The indicator inset tracks the visible expansion. Inset changes preserve collapse fraction and scrolling beyond collapse, and removal restores only the package's contribution. The coordinator observes the selected scroll view without replacing its delegate. Without a selected scroll view, content remains below the entire header.

The Xcode sample links the local Swift package product. Its storyboard constructs the package navigation controller, while app-only subclasses implement the demonstration controls. Public API tests import only the package module. The app test target also compiles that same test source so the shared app scheme executes it reliably; Xcode omits test configurations from its dependency package scheme. App integration tests exercise storyboard loading and scene layout, while UI tests exercise complete interactions.

The wrapper API uses standard child-controller containment and reads buttons/display mode from the content controller's navigation item. Direct subclasses use their own navigation item. The visible bar has a separate item representation; item objects retain UIKit action/menu/custom-view semantics. Item snapshots refresh after loading, on appearance, and through `reloadNavigationItems()`. Ordinary pushes/segues, search controllers, and specialized container preferences are not intercepted. See [adoption](adoption.md) for those boundaries. The system edge recognizer keeps UIKit's target/action with a narrow public delegate gate; this remains a regression-test area for every supported OS.
